## F4 — Corrección del hallazgo H6 en `docs/engineering/model_training_pipeline.md`

### F4.1 — Verificación del dato incorrecto

El texto original afirmaba: *"El `.env` versionado tiene `DATABASE_URL=…@localhost:5432…`"*.
**Falso**:

```
$ git ls-files | grep -E '\.env$'
(ninguno)
$ git ls-files | grep -iE '(^|/)\.env'
.env.example
backend_api/.env.example
frontend/.env.example
malaria_dataset_split_project/.env.example
malaria_dl_local_project/.env.example
```

`.gitignore:38-40` → `.env` / `.env.*` ignorados, solo `!.env.example`. Ningún `.env` real
está versionado — **misma constatación previa** en
[`architecture_audit_2026-09-08.md`](architecture_audit_2026-09-08.md) §6 punto 5
(*"Ambos archivos no están versionados (confirmado con `git ls-files`)"*). Además, los
`.env.example` versionados **no** definen `DATABASE_URL`: declaran que lo inyecta Docker
Compose (`git show HEAD:.env.example` línea 15, `git show HEAD:malaria_dl_local_project/.env.example`).

El problema real (que sí persiste): `persistence/database.py` carga `PROJECT_ROOT/.env`
(`:14`, `:52`) y `normalize_database_url` exige hostname `db` (`:42`) y puerto `5432`
(`:44`). Correr `src.train` / `run_train_all_models.py` en el host exige, o el contenedor
`backend`, o una config local **no versionada** con `DATABASE_URL` de host `db` resoluble
(p. ej. entrada `db` en `/etc/hosts`). Un `DATABASE_URL` local con host `localhost` es
rechazado por `database.py:42` **antes** de conectar — verificado en vivo en la tarea de
diagnóstico: `resolve_governed_dataset('d8c0cab5-…')` lanzó
`RuntimeError: "DATABASE_URL solo permite el hostname db"`.
