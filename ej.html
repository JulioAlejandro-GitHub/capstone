# Tarea: Migrar `frontend` → `frontend2` usando exclusivamente Tailwind CSS # Rol Eres el responsable técnico de la migración de estilos. Tu único objetivo es replicar `frontend/` en `frontend2/` con la misma lógica y Tailwind CSS como único sistema de estilos. No refactors, no optimizas, no inventas funcionalidad. ## Restricciones - NO refactors. Si el código original es feo, replicalo feo. - NO inventes componentes, rutas ni servicios que no existan en `frontend/`. - NO optimices performance, no agregues memoización, no cambies patterns. - Si algo no está claro, preguntá antes de asumir. ## Contexto - En este repo existe un subsistema `frontend/` que funciona correctamente. - Debes crear un nuevo subsistema `frontend2/` que replique **exactamente** las mismas funcionalidades, pero usando **únicamente Tailwind CSS** para toda la presentación. ## Reglas estrictas 1. **`frontend/` es SOLO LECTURA.** No modifiques ningún archivo dentro de `frontend/`. 2. **`frontend2/` replica la estructura COMPLETA de `frontend/`:** - Routing (rutas, guards, lazy loading, redirects) - Componentes (todos: primitivas, feature, layouts, páginas) - Hooks (custom hooks, context providers) - Services / API calls (fetch, interceptors, mutaciones) - Utilidades y helpers - Tipos / interfaces / schemas - Estado global (store, reducers, slices) - Configuración (env vars, feature flags, constants) - Test files (si existen) 3. **La ÚNICA diferencia permitida entre `frontend/` y `frontend2/` es la capa de estilos:** - En `frontend/`: styled-components / CSS Modules / MUI / lo que use. - En `frontend2/`: exclusivamente Tailwind CSS utilities. 4. **Prohibido en `frontend2/`:** CSS-in-JS, CSS Modules, SASS, LESS, MUI, Chakra, o cualquier librería que inyecte estilos. 5. **La lógica es idéntica.** No refactorices, no optimices, no cambies nombres de funciones. Si el componente original tiene un bug, replicalo igual (no lo arregles). ## Proceso 1. **Explora** `frontend/` completo (no solo componentes con estilos). 2. **Crea la estructura espejo** en `frontend2/`: - Mismas carpetas, mismos nombres de archivo. - Config de Tailwind + punto de entrada con `@import "tailwindcss"`. 3. **Migra por capas, de dependencia a dependiente:** - Onda 0: config, tipos, utils, services, hooks (sin estilos → se copian tal cual) - Onda 1: primitivas de UI (Button, Input, Badge, ...) - Onda 2: componentes de feature - Onda 3: layouts, páginas, routing 4. **Para cada archivo:** - Si NO tiene estilos → cópialo tal cual a `frontend2/` (cambiando solo paths de import si la estructura lo requiere). - Si SÍ tiene estilos → replica la lógica y reemplaza los estilos por Tailwind. 5. **Actualizá `MIGRATION_MAP.md`** después de cada archivo migrado. 6. **DETENE** al terminar la onda. Reportá y esperá. ## Definición de terminado - `frontend2/` compila y sirve sin errores. - Todas las rutas y funcionalidades de `frontend/` existen en `frontend2/`. - No hay ningún archivo `.css` con reglas propias (solo el import de Tailwind). - No hay imports de librerías de estilos (styled-components, emotion, MUI, etc.). - `frontend/` no ha sido modificado en ningún momento. ## Formato de respuesta Trabaja en pasos. Para cada componente migrado, indica: - Ruta original → ruta nueva - Notas sobre decisiones de mapeo (solo si no es obvio)
